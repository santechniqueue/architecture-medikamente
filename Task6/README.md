# Задание 6. Движок классификации данных

## Архитектура движка классификации

### Общее описание

Движок классификации данных (Data Classification Engine) представляет собой пайплайн обработки данных, который автоматически определяет уровень конфиденциальности каждого поля/записи перед загрузкой в аналитическое хранилище. Движок учитывает, что структуры данных на входе подвержены изменениям и не размечены заранее.

### Источники данных

Движок принимает данные из внутренних источников. Каждый источник подключается к определённому этапу пайплайна в зависимости от формата и протокола поступления данных.

| Источник                                | Описание                                | Точка входа              |
|-----------------------------------------|-----------------------------------------|--------------------------|
| CRM (PostgreSQL)                        | Профили пациентов, записи, договоры     | Data Ingestion           |
| Хранилище мед. данных (PostgreSQL + S3) | Медкарты, диагнозы, сканы документов    | Data Ingestion           |
| Платёжный шлюз                          | Транзакции, чеки, возвраты              | Data Ingestion           |
| 1С:Бухгалтерия                          | Зарплаты, кадры, налоги, ТМЦ            | Schema Detection         |
| Сервис записей (PostgreSQL)             | Расписание, слоты записи                | Schema Detection         |
| Сервис лаб. данных (PostgreSQL)         | Результаты анализов, реестры            | PII Scanner              |
| Логи и аудит                            | Журналы доступа, действия пользователей | Classification & Tagging |

### Компоненты пайплайна

**Основной пайплайн:**

1. **Data Ingestion** - приём данных через Apache Kafka и Debezium CDC. Нормализация форматов в JSON. Валидация схемы через Schema Registry.
   - Входящие источники: CRM, Хранилище мед. данных, Платёжный шлюз
   - Выход: Raw Layer (Bronze)

2. **Schema Detection** - автоматическое определение структуры входных данных. Обнаружение изменений схемы.
   - Входящие источники: 1С:Бухгалтерия, Сервис записей
   - Связь: Quality Gate (валидация качества данных)

3. **PII Scanner** - обнаружение персональных данных в каждом поле:
   - RegEx-паттерны: телефоны, email, ИНН, СНИЛС, паспортные данные, даты рождения
   - NLP-модель: обнаружение ФИО, адресов, медицинских терминов (диагнозы, анамнез, хронические заболевания)
   - ML-классификатор: финансовые данные (платёжные данные, зарплатные ведомости), договоры, кадровые данные
   - Специальные правила: согласия на обработку ПДн, журналы аудита, реестры анализов лаборатории, email-переписка
   - Каждому полю присваивается confidence score (0.0–1.0)
   - Входящий источник: Сервис лаб. данных
   - Связи: Policy Engine (правила PII) > Alert Manager (алерты)

4. **Classification & Tagging** - на основе результатов PII Scanner каждому полю/записи присваивается тег конфиденциальности:
   - `PUBLIC` - общедоступные данные
   - `INTERNAL` - внутренние данные компании
   - `CONFIDENTIAL` - персональные данные
   - `RESTRICTED` - специальная категория ПДн, врачебная тайна

   Теги записываются в Apache Atlas с Data Lineage. Перед тегированием выполняется проверка наличия согласия субъекта ПДн через Consent Service API. Данные без действующего согласия блокируются и направляются на ручную обработку.
   - Входящий источник: Логи и аудит
   - Связи: > Metadata Catalog > Metrics & Audit, Consent Check
   - Выход: Classified Layer (Silver)

5. **Data Transformation** - трансформация данных в зависимости от тега:
   - `PUBLIC/INTERNAL` > без изменений
   - `CONFIDENTIAL` > псевдонимизация (замена ФИО на UUID), маскирование
   - `RESTRICTED` > шифрование полей (AES-256-GCM), токенизация, обезличивание для аналитики
   - Выход: Anonymized Layer (Gold), Sensitive Data Vault (RESTRICTED)

**Вспомогательные сервисы:**

- **Policy Engine (OPA)** - правила классификации и трансформации в декларативном виде. Версионирование политик. Связь: PII Scanner.
- **Metadata Catalog (Apache Atlas)** - каталог метаданных, Data Lineage, владельцы данных. Связь: Classification & Tagging.
- **Quality Gate (Great Expectations / Deequ)** - валидация качества данных, проверка полноты, формата. Отклонение некачественных батчей. Связь: Schema Detection.
- **Consent Check** - проверка наличия согласия субъекта ПДн перед обработкой. Интеграция с Consent Service API. Блокировка данных без действующего согласия. Связь:  Classification & Tagging.
- **Metrics & Audit** - экспорт метрик в Prometheus + Grafana: precision, recall, F1, throughput, latency. Аудит всех операций классификации. Связь: Classification & Tagging.
- **Alert Manager** - оповещения при обнаружении неклассифицированных ПДн, изменениях схемы, отсутствии согласия, аномалиях. Связь: PII Scanner.

### Организация слоёв в хранилище данных

| Слой                     | Назначение                                                                                        | Защита                                                                              | Доступ                                                |
|--------------------------|---------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------|-------------------------------------------------------|
| **Raw (Bronze)**         | Исходные данные AS-IS для повторной обработки                                                     | AES-256 at rest, TTL 30 дней                                                        | Только ETL-сервис (service account)                   |
| **Classified (Silver)**  | Данные с тегами конфиденциальности                                                                | CONFIDENTIAL/RESTRICTED поля зашифрованы                                            | RBAC по тегам                                         |
| **Anonymized (Gold)**    | Полностью обезличенные данные для BI/ML/AI                                                        | Стандартная защита                                                                  | Аналитики, BI-инструменты                             |
| **Sensitive Data Vault** | Изолированное хранилище для RESTRICTED (мед. карты, результаты анализов, хронические заболевания) | Отдельный PostgreSQL, field-level encryption (AES-256-GCM через Vault Transit), MFA | Только через Privacy Layer + аудит + проверка consent |
| **Archive (Cold)**       | Данные с истёкшим TTL                                                                             | Зашифрованы + сжаты (Zstd)                                                          | По запросу + одобрение                                |

## Метрики эффективности классификации

### Метрики качества классификации

| Метрика                           | Описание                                                             | Целевое значение | Как помогает оптимизации                                                                                |
|-----------------------------------|----------------------------------------------------------------------|------------------|---------------------------------------------------------------------------------------------------------|
| **Precision**                     | Доля правильно классифицированных как ПДн из всех помеченных как ПДн | >= 95%           | Снижает ложноположительные срабатывания > меньше данных шифруется без необходимости > экономия ресурсов |
| **Recall**                        | Доля обнаруженных ПДн из всех реальных ПДн                           | >= 99%           | Минимизирует пропуск конфиденциальных данных > снижает риск утечки                                      |
| **F1-Score**                      | Гармоническое среднее Precision и Recall                             | >= 97%           | Баланс между безопасностью и производительностью                                                        |
| **Confidence Score Distribution** | Распределение оценок уверенности PII Scanner                         | Медиана > 0.9    | Поля с низким confidence > ручная проверка > дообучение модели                                          |
| **Misclassification Rate**        | Процент ошибочно классифицированных полей                            | < 1%             | Идентификация слабых мест в правилах/модели                                                             |

### Метрики производительности

| Метрика                   | Описание                                         | Целевое значение  | Как помогает оптимизации                            |
|---------------------------|--------------------------------------------------|-------------------|-----------------------------------------------------|
| **Throughput**            | Количество записей, обработанных в секунду       | >= 10 000 rec/sec | Определяет, справляется ли система с объёмом данных |
| **Latency**               | Время обработки одной записи через весь пайплайн | < 100 мс          | Обнаружение бутылочных горлышек в пайплайне         |
| **Batch Processing Time** | Время обработки полного ежедневного батча        | < 2 часов         | Планирование окна загрузки данных                   |
| **Queue Depth**           | Размер очереди Kafka                             | < 100 000         | Раннее обнаружение отставания обработки             |

### Метрики Data Quality

| Метрика                 | Описание                                 | Целевое значение                 |
|-------------------------|------------------------------------------|----------------------------------|
| **Schema Drift Rate**   | Частота изменений схемы входных данных   | Мониторинг (алерт при изменении) |
| **Data Completeness**   | Процент заполненных обязательных полей   | >= 99%                           |
| **Duplicate Rate**      | Процент дубликатов записей               | < 0.1%                           |
| **Rejected Batch Rate** | Процент батчей, отклонённых Quality Gate | < 5%                             |

## Масштабируемость (Scalability)

### Горизонтальное масштабирование

| Компонент                    | Стратегия масштабирования                                                                                           |
|------------------------------|---------------------------------------------------------------------------------------------------------------------|
| **Data Ingestion (Kafka)**   | Увеличение числа партиций в топиках. Добавление брокеров в кластер. Consumer groups для параллельной обработки      |
| **PII Scanner**              | Stateless-сервис в Kubernetes. HPA (Horizontal Pod Autoscaler) по CPU/памяти. Партиционирование данных по источнику |
| **Classification & Tagging** | Stateless-сервис. HPA. Шардирование по филиалу                                                                      |
| **Data Transformation**      | Stateless-сервис. HPA. Параллельная обработка через Kafka consumer groups                                           |
| **Analytical Storage**       | PostgreSQL с Citus для Classified Layer. ClickHouse для Anonymized Layer. S3-совместимое хранилище для Raw Layer    |

### Вертикальное масштабирование

| Компонент                        | Стратегия                                      |
|----------------------------------|------------------------------------------------|
| **PII Scanner (ML-модель)**      | GPU-ускорение для NLP-модели при росте объёмов |
| **PostgreSQL (Sensitive Vault)** | Увеличение RAM и SSD для критичного хранилища  |
| **Apache Atlas**                 | Увеличение ресурсов JVM и HBase/Solr backend   |

### План масштабирования при росте

| Сценарий               | Текущий объём | 5x рост | Действия                                                                     |
|------------------------|---------------|---------|------------------------------------------------------------------------------|
| Пациенты               | ~1000         | ~5000   | HPA для CRM и PII Scanner. Дополнительные партиции Kafka                     |
| Записей/день           | ~100          | ~500    | Без изменений (запас мощности)                                               |
| Филиалы                | 1             | 5+      | Шардирование по филиалу. VPN между филиалами. Локальный кеш в каждом филиале |
| Аналитических запросов | Единицы       | Десятки | Materialized Views в ClickHouse. Кеширование в Redis                         |
| Источники данных       | 7             | 15+     | Добавление Kafka-коннекторов. Schema Registry для новых схем                 |

### Архитектурные решения для масштабируемости

1. **Event-driven architecture** - Kafka обеспечивает буферизацию и развязку источников от потребителей. При росте нагрузки достаточно добавить consumer'ов.
2. **Stateless-сервисы** - все компоненты пайплайна (Ingestion, Scanner, Classifier, Transformer) не хранят состояние. Масштабирование - добавление подов в Kubernetes.
3. **Partitioning strategy** - данные партиционируются по филиалу, что обеспечивает изоляцию и параллельную обработку.
4. **Caching** - Redis для кеширования правил классификации и результатов PII Scanner для повторяющихся паттернов.
5. **Medallion Architecture** (Bronze-Silver-Gold) - позволяет перерабатывать данные из Raw Layer при изменении правил классификации без повторного извлечения из источников.
