# Задание 5. Cutover-план миграции «Медикаменте»

## Выбор стратегии и миграции

Выбранная стратегия: High-level design с применением Strangler Fig в существующих сервисах.

**Преимущества для данного сценария:**
1. **Процессы** - многие рабочие процессы компании находятся на начальном этапе: сбор данных, менеджмент журналов, карточек и тд в ручном режиме. Это позволяет выстроить и спроектировать процесс автоматизации почти с нуля.
2. **Нет двойного ввода данных** - текущий учёт ведётся в Excel-файлах на сервере. При Parallel Run пользователи и пациенты должны были бы заполнять данные дважды (в старую и новую систему), что неприемлемо для клиники с 35 сотрудниками разного уровня IT-грамотности.
3. **Поэтапная замена модулей** - Strangler Fig позволяет заменять legacy-компоненты по одному: каждый модуль (CRM, записи, мед. данные, лаб. данные) мигрируется и переключается независимо. Пользователи работают в одной системе и процессе - либо старой, либо новой.
4. **1С не затрагивается стратегией** - 1С:Бухгалтерия и 1С:Торговля продолжают работать; их перевод на клиент-серверный режим происходит параллельно и независимо от миграции основных модулей.
5. **ККМ покрывается Strangler Fig** - адаптер TCP/IP + REST выступает как strangler-прокси: ККМ продолжают работать через старый протокол, а адаптер перенаправляет данные в новый Платёжный шлюз.

**Ограничения стратегии:**
- Период сосуществования old/new может быть длительным (до 6 месяцев), что требует поддержки обеих систем.
- Необходимо проектирование с нуля (high-level design) всей целевой архитектуры до начала миграции.
- Требуется чёткое определение bounded contexts (DDD) для правильной декомпозиции на микросервисы, чтобы избежать распределённого монолита.
- ETL-миграция данных из Excel в PostgreSQL остаётся сложной задачей (неструктурированные данные, дубли, скрытая бизнес-логика).

**Альтернативы:**
- **Parallel Run** - подошёл, если процессы компании уже существовали в рамках написанных решений. Сотрудники клиники (ресепшен, врачи, админ) не готовы заполнять информацию дважды. Синхронизация Excel и PostgreSQL в реальном времени создаёт гонки данных. Пациенты не будут заполнять формы в двух системах.
- **Branch by abstraction** - требует высокую экспертизу в рефакторинге и наличие кодовой базы. При текущем стеке (Excel + 1С файловый режим) нет кода, который можно рефакторить слой за слоем.

## Критерии успешности миграции

| Критерий                        | Метрика                                                | Пороговое значение   |
|---------------------------------|--------------------------------------------------------|----------------------|
| Целостность данных              | % записей, прошедших верификацию в PostgreSQL          | 100%                 |
| Доступность системы             | Uptime после переключения каждого модуля               | >= 99.5%             |
| Производительность              | Время отклика API                                      | < 500 мс             |
| Безопасность                    | Количество инцидентов с ПДн                            | 0                    |
| Покрытие шифрования             | % CONFIDENTIAL/RESTRICTED полей с AES-256-GCM          | 100%                 |
| Покрытие согласий               | % пациентов с оформленным consent                      | 100%                 |
| DLP false positive rate         | Доля ложных срабатываний DLP                           | < 5%                 |
| Время отката модуля             | Время переключения перехода процесса обратно на legacy | < 5 мин              |
